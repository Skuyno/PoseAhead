# Desktop-панель PoseAhead

## Запуск

Двойной клик по `StartPoseAhead.cmd` в корне проекта. Нужна уже установленная
локальная `.venv`; launcher не скачивает и не устанавливает зависимости.
Альтернативно из корня:

```powershell
.venv/Scripts/python.exe main.py gui
# Или: poetry run poseahead gui
```

Панель сделана на Tkinter, доступном в текущем Python 3.10. Она не запускает
web-сервер и не меняет настройки VPN, адаптеров или firewall. Источник движения
выполняется в отдельном процессе: загрузка модели и камера не блокируют Tk-поток.
В запуске через pythonw worker использует соседний python.exe без видимой консоли,
с перенаправленными stdin/stdout. Core/обычный CLI не импортируют GUI или CUDA.
Live orchestration находится в `poseahead.runtime.webcam`; worker вызывает его
напрямую. Скрипт `scripts/benchmark_webcam.py` остаётся совместимым launcher'ом,
но не является зависимостью desktop runtime.

## Сохранение настроек

Начиная с 2026-10-18, панель запоминает источник, метод, длительность, индекс камеры,
порт, горизонт и пути выбранных файлов/Unity в `outputs/desktop_settings.json`.
Настройки сохраняются после успешного старта и при обычном закрытии; запись идёт
через временный файл и атомарную замену, не через редактирование live JSON.
Восстановление только заполняет форму: камера, Unity и producer не запускаются.
Флажок сохранения raw камеры намеренно **не запоминается** и при открытии выключен.

Повреждённый, слишком большой или несовместимый файл настроек не мешает открыть UI:
используются начальные значения, в журнале есть предупреждение. Исходный файл не
перезаписывается; для возобновления сохранения переименуйте его и перезапустите
панель. Отсутствующие конфигурации/записи не подменяются: при старте потребуется
выбрать существующий файл. Ошибка сохранения настроек не прерывает producer.

## Быстро посмотреть аватар

Перед показом можно выбрать готовый сценарий в верхней строке и нажать
«Применить · без запуска». Доступны тестовые позы, CMU 13/29 + Калман-CV 100 мс,
тот же CMU + экспериментальный adaptive с partial recovery и короткая сохранённая
MeTRAbs-запись. Применение не начинает поток, не включает камеру, сохраняет выбранный
порт/настройки камеры и не меняет исследовательские или live-default конфигурации.
Отсутствующие записи/checkpoint не заменяются другими; ошибка показывается до
применения. Для adaptive проверяются закреплённые manifest-хеши; веса полностью
проверяются worker при загрузке. Во время сессии переключение недоступно.

Все сценарии идут в исходном темпе без циклов и искусственного шума. Это проверка
интеграции, не доказательство нейросетевого преимущества; количественные результаты
показываются отдельно. [DOCX-гайд](demo_guide.docx) и [текстовый гайд](demo_guide.md)
содержат сценарий встречи, live-настройки, результаты и варианты при сбоях.
Обе колонки панели прокручиваются независимо, чтобы журнал/Stop оставались доступны.

Для встречи с научным руководителем подготовлены актуальный
[отчёт с результатами и порядком показа](../output/pdf/poseahead_advisor_report_20261020.pdf)
и [отдельный текст выступления](advisor_speech_20261020.md) от 20 октября.
Показ на записях не требует камеры. Отчёт отделяет проверенный прототип и
validation-результаты от незавершённой live-приёмки и недоказанного выигрыша по задержке.

1. Нажать «Открыть проект Unity». Кнопка сверяет версию executable с
   `ProjectVersion.txt`; сейчас нужна 6000.3.23f1. Если проект уже открыт,
   используется существующее окно без запуска второго Editor.
2. В Unity открыть `Assets/PoseAhead/Scenes/PoseAheadDiagnostic 1.unity`, нажать Play.
3. В панели выбрать «Тестовые движения · 8 секунд», метод Raw и порт 5005.
4. Нажать «Запустить». Последовательность закончится примерно через восемь секунд,
   даже если выставлен больший лимит длительности. Автоматического зацикливания нет.

Unity остаётся отдельным окном; панель не встраивает viewport и не нажимает Play
сама. Не открывает/не сохраняет чужие несохранённые сцены и не закрывает Unity.
Искусственные восемь поз — проверка направления движения, не исследовательский датасет.

## Источники и методы

- **Тестовые движения:** без камеры/GPU, диагностические позиции и перемещение root.
- **Запись движения · NPZ:** существующая запись воспроизводится в исходном темпе.
  Входной файл и исследовательские timestamps не меняются; wire-копии используют
  уже реализованное display-only перебазирование часов.
- **Камера · MeTRAbs:** индекс камеры, существующий JSON live-конфигурации и лимит
  длительности. Для новой записи включить «Сохранять исходные наблюдения камеры в NPZ».
  Сохраняются позы, включая пропуски; изображения с камеры не записываются.

Доступны Raw, EMA, One-Euro, Kalman, Kalman + экстраполяция. Для последнего выбирается
горизонт 33/66/100/150 мс. Более точные параметры и experimental MLP выбираются через
«Из JSON · включая MLP». Горизонт MLP задаётся выбранным checkpoint/config, а не
выпадающим списком экстраполяции. Для MLP с камерой требуется явный `linear_past`.
Никакой checkpoint не назначается победителем или live-default автоматически.
Весь интерфейс пока управляет демонстрацией; обучение/эксперименты остаются в CLI.

Формы показывают только относящиеся к выбранному источнику/методу поля. Настройки
фиксируются на время сессии; смена метода происходит между сессиями и сбрасывает
историю процессора. Индекс камеры и порт панели явно перекрывают эти поля JSON.
Остальные параметры live JSON, включая intrinsics, сохраняются. Desktop разрешает
только host `127.0.0.1`; порт должен совпадать с Unity receiver.

### Быстрый профиль MeTRAbs

В режиме камеры у строки live JSON есть кнопка «Быстрый профиль». Она не запускает
камеру: создаёт отдельный JSON в `outputs/live_profiles/`, меняя только
`crop_precision` на `fp16_conv`. Калибровка и все остальные выбранные параметры
сохраняются, исходный JSON не меняется. Если текущий профиль уже быстрый, лишняя
копия не создаётся. Индекс камеры и порт по-прежнему берутся из формы.
Во время активного producer кнопка недоступна.

Ускорение получено предварительным хранением весов свёрток MeTRAbs в FP16,
при FP32-параметрах BatchNorm и неизменённом геометрическом пути. Обычный `autocast`
остаётся default. На проверенных
записях массивы поз/root/confidence и tracking совпали точно, но ускорение и
live-бюджеты на камере пока не подтверждены. Для возврата выберите исходный JSON.
Готовый `configs/live/fp16_conv.json` использует стандартные параметры без
пользовательской калибровки; кнопка безопаснее при наличии своих intrinsics.
Протокол, цифры и ограничения: [проверка производительности](metrabs_performance.md).

## Что означают показатели

- **Полных поз / с · камера:** число полностью валидных 17-joint поз за время
  измерения; не render FPS. Для диагностического/NPZ replay стоит «—».
- **UDP-пакетов отправлено:** успешные локальные send-вызовы. Это не число поз,
  применённых в Unity: latest-frame слот может пропускать промежуточные кадры.
- **Capture → send · p95:** время от доступности захваченного кадра до окончания
  локальной отправки. Не включает подтверждённый приём и отображение Unity;
  не является effective latency. Для replay стоит «—».

Во время камеры блок «Сессия» показывает медианы возраста кадра до начала 3D,
полного MeTRAbs backend и записи/temporal processing. В progress и report.json
есть `pipeline_latency_ms` с полными этапами, включая подготовку/отправку пакета.
Нельзя складывать p95 отдельных этапов: наборы кадров различаются, а percentile
суммы не равен сумме percentile. Несостоявшаяся отправка имеет samples = 0/null,
а не выдуманные 0 мс. Это host timing, не задержка камеры до монитора.

Пакеты поз по-прежнему однонаправленные. Во время сессии worker примерно раз в
0,5 с вместе с producer-прогрессом читает локальный
`unity/PoseAheadAvatar/Temp/PoseAheadTelemetry-<port>.json`, который обновляет
компонент диагностической сцены. Приём подтверждается только свежим snapshot
с совпадающими session ID и портом; чужой/старый/повреждённый файл и невозможный
счётчик received > sent не засчитываются. В панели сразу видны received/applied,
измеренный render FPS (если доступен) и ошибки receiver/rig. Если новые данные
перестают поступать, подтверждение снимается не позднее двух секунд возраста
последнего snapshot, даже при зависшем/молчащем producer. Это не диагноз причины
сбоя и не гарантия отрисовки на монитор. Итоговая проверка выполняется ещё раз
после завершения; подтверждённый итог остаётся историческим результатом прогона.
В панели появляются число принятых пакетов, число поз, изменивших хотя бы одну
кость, и средний render FPS за окно Unity. Между приёмом и применением поз часть
кадров может быть пропущена latest-frame слотом — это не потеря UDP.
Render FPS считается по завершениям Game-camera render в текущем built-in pipeline,
с исключением Scene View/RenderTexture и дубликатов кадра. Он **не измеряет**
показ изображения монитором. Headless/batch-прогон не засчитывается; в нём FPS `null`.
В Unity overlay показывается мгновенный **update FPS**, а не render FPS.
Во время Play диагностическое демо задаёт `Application.targetFrameRate = 60` и
временно отключает VSync. Это бюджет рендера, а не частота распознавания поз или
обещание ровных 60 FPS. `DemoFrameRateScope` учитывает перекрывающиеся экземпляры
демо и возвращает исходные настройки после отключения последнего; если другой
скрипт изменил настройки, его изменение не перезаписывается. В Edit Mode лимит
автоматически не применяется. Настройки других приложений/драйвера не меняются.
Unity-снимок отдельно содержит `target_frame_rate`, `v_sync_count` и
`demo_frame_limit_active`; измеренный `render_fps` по-прежнему считается по событиям.
В Editor лимит касается Game view, но не всех окон Editor
([Unity API](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Application-targetFrameRate.html)).
Без полной позы камера может показывать 0 valid FPS; панель предлагает проверить
человека в кадре, а не объявляет успешный tracking.

Сравнение после лимита рендера: сначала короткий 30-секундный live-прогон с теми же
настройками (`raw`, камера 0), человеком целиком в кадре и видимым Game view.
Сравнивать valid FPS и capture-to-send p95, одновременно проверять измеренный
Unity render FPS и совпадение sent/received/applied. Предыдущий десятиминутный прогон
`outputs/ui_20261005_140958_4ed33ebe/` дал 18.01 valid FPS, p95 98.43 ms и около
706.62 Unity render callbacks/s. Лимит пока не доказывает причину торможения или
прирост производительности; разная длительность, движения и загрузка машины
делают такое сравнение ориентировочным, не контролируемым A/B-экспериментом.
Проверка кода лимита 2026-10-05: C# smoke и сборка против API установленной Unity
прошли; четыре native-теста в `outputs/unity_native_20261005_143910_da62a79d/`
проверили восстановление настроек, перекрытие scope и настоящий Python → Unity
replay с `target_frame_rate = 60`, `v_sync_count = 0`. Эти тесты headless: они не
подтверждают измеренные 60 render FPS или ускорение live inference.

## Остановка и результаты

При запуске камеры панель и `worker.log` показывают отдельные этапы: импорт PyTorch,
проверку исходников и локальных весов, подготовку CUDA/MeTRAbs/YOLO, открытие камеры,
затем ожидание кадра и оценку позы для каждого кадра прогрева. Открытие камеры больше
не скрывается под надписью о загрузке CUDA. Проверка Git ограничена 10 секундами и не
наследует канал команд UI.

На Windows поток команд проверяет доступные байты через `PeekNamedPipe` и читает
только их; блокирующее ожидание строки на stdin запрещено. Оно воспроизводимо
зависало при загрузке native-библиотек и проверке Git. Частичные команды собираются
до перевода строки, размер буфера ограничен; поток завершается вместе с сессией.

«Остановить» передаёт cooperative stop своему worker. Replay прерывается также
внутри длинных промежутков записи (проверка не реже 50 мс). Камера завершается между
вызовами capture/inference, освобождает ресурсы и сохраняет накопленный raw NPZ.
CUDA/model loading и заблокированные native-вызовы не могут быть мгновенно прерваны.
При загрузке модели Stop проверяется между этапами; отмена до измерения не открывает
камеру и не создаёт фиктивный NPZ. Уже начатый native-вызов сначала должен вернуться.
Если остановка затянулась, появляется доступная кнопка принудительного завершения
с явным предупреждением о потере несохранённых наблюдений. Завершается только
собственный worker, не чужой Python/Unity или процессы VPN.

Проверка исправления 2026-10-05: 553 Python-теста прошли, включая native-import
при открытом command pipe, частичные команды и отмену на этапах запуска.
Настоящий UI-worker с CUDA и камерой 0 прошёл прогрев и обработал 60 кадров за
двухсекундное измерение (`outputs/ui_20261005_135604_822b0907/`); полных поз не
обнаружено, поэтому это проверка запуска, а не успешного tracking человека.
Stop во время подготовки модели завершился с `stopped_before_measurement` до
открытия камеры (`outputs/ui_20261005_135720_6ad6b403/`). Изображения и raw NPZ
в этих проверках не сохранялись. Это не заменяет десятиминутный live-gate.

При закрытии активной панели сначала запрашивается остановка; окно закрывается
после завершения worker. Повторное закрытие позволяет запросить принудительную
остановку. Unity остаётся открытым. Сбой камеры/модели не объявляется успехом.

Каждой сессии выделяется новый `outputs/ui_<time>_<random>/`:

- `request.json` — выбранные настройки панели;
- `processor.json` — отдельная копия эффективной конфигурации; checkpoint-пути
  разрешены относительно исходного JSON, который не меняется;
- `worker.log` — вывод worker (ограничен примерно 4 MiB); экранный журнал — 300 строк;
- `report.json` — итог существующего runtime/benchmark после успешного завершения;
- `run_report.json` — единый отчёт Python/Unity: capture → send, валидные позы,
  пропуски камеры, RAM/VRAM, принятые/применённые позы и render FPS, если измерены;
- `observations.npz` — raw camera observations, только если запрошены и получены.

Если остановка произошла до измерения/наблюдений, NPZ не выдумывается: путь записи
в отчёте `null`. При ошибке итогового отчёта может не быть; смотрите журнал и код
выхода. Existing data/reports не перезаписываются. Queue событий UI ограничена 200
записями. Настройки формы сохраняются отдельно от сессионных артефактов.

Измерение RAM/VRAM камеры начинается **после прогрева**, включает начальную и
финальную точки и периоды без кадров. RAM — текущий working set, не peak RSS.
Отдельные проверки роста RAM ≤128 MiB и reserved VRAM ≤32 MiB требуют ≥590 с;
короткий тест получает `insufficient_duration`. Это не автоматически успешная
приёмка всей системы: `acceptance_status` остаётся `not_assessed`.
Unity измеряет RAM собственного Editor-процесса, не отдельно сцены; недоступный
замер представлен `null`, а не нулевым потреблением. Окно Unity начинается с
наблюдения этой сессии и может включать сохранение записи/отчёта и до 0,65 с
финального ожидания телеметрии;
его длительность находится в `unity.duration_s`, отдельно от Python benchmark.
Разность отправленных/принятых пакетов называется `unconfirmed_pose_frames`,
не доказанной потерей сети. Счётчик rejected относится к receiver целиком.

Для живой приёмки: открыть сцену в Unity и Play, выбрать камеру, выставить
длительность 600 с, при желании включить raw NPZ и находиться целиком в кадре.
После завершения открыть результаты и проверить `run_report.json`. Требуется
реальный человек; прогон на записи или без графики не закрывает M1/M3.
